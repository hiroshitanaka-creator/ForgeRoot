# PR Review Method(非エンジニアと一緒にPRを判断する方法)

ユーザーが「open PRをレビューして」「何をマージすべき？」と言ったら、この手順で行う。
ゴールは、ユーザーが**マージボタンを押すか押さないかを自信を持って決められる**状態にすること。

## Codexの手順

1. **PRの基本情報を取る**: 番号 / タイトル / draft状態 / base / head / 作成日 / diff
2. **鮮度を判定する**: base が今の main と一致しているか。古い main ベースなら「stale(=載せ替えが必要)」
3. **重複を判定する**: 同じT番号・同じ目的の open PR が他にないか
4. **スコープを判定する**: 1 issue = 1 bounded PR を守っているか。無関係な変更が混ざっていないか
5. **危険パスを判定する**: safety-boundaries.md の class C/D パスに触れていないか。触れていたらその行だけ詳説する
6. **検証を再現する**: PR本文のtest planを**実際にローカルで実行**する(checkoutして回す)。実行できなければ「未検証」と明記
7. **秘密情報を確認する**: diffに token / secret / 内部URLが含まれていないか
8. **判定を出す**: 下の4択で

## 判定の4択

| 判定 | 意味 | ユーザーへの案内 |
|---|---|---|
| マージ推奨 | 検証済み・境界内・重複なし | 「Merge pull request を押してOK」+ 取り消し方法 |
| 条件付き推奨 | 軽微な修正で通る | Codexが修正を同ブランチにpushしてから再提示 |
| 保留 | 判断材料が不足 | 不足している証拠と、それを得る手順を提示 |
| 不採用推奨 | 重複・境界違反・設計矛盾 | closeを提案。**closeボタンはユーザーが押す** |

## ユーザーへの報告形式

```
PR #<番号>: <一言でいうと何をするPRか>
鮮度: fresh / stale(理由)
重複: なし / PR #X と重複
危険パス: なし / あり(どこが・なぜ)
検証: 何を実行し、結果はどうだったか(未実行なら未実行と書く)
判定: 上の4択
あなたが押すボタン: <具体的な場所>
取り消したくなったら: <rollback手順>
```

## 非エンジニア向けの説明ルール

- diff全文を見せない。「変わるファイル数」「追加/削除行数」「危険箇所の有無」に要約する
- 危険箇所が**ある場合のみ**、該当行を引用して日本語で何が起きるか説明する
- 「このPRをマージすると何ができるようになるか」を1文で言う
- 「マージしなかった場合何が起きるか」も1文で言う(比較材料)

## 指摘修正の総ざらい手順(点修正禁止ルールの実行方法)

レビュー指摘を直すときは、diffに見えている行だけでなく**影響範囲と依存関係**まで監査する。手順:

1. **指摘の一般化**: 各指摘を「このコードだけの問題」ではなく「パターン」として言い換える(例:「confidenceがNaNを素通り」→「数値フィールドの有限性検証が全体的に無い」)
2. **水平展開grep**: 一般化したパターンで対象package全体と兄弟packageを検索する。同じヘルパー・同じ正規表現・同じ構造のコピペ先を全部列挙する。**ただし修正するのはPRの宣言済みmutable paths内のみ**。範囲外・class C/Dパスでの発見はfollow-upタスクとして記録し、User Decision Cardで報告する(1 issue = 1 bounded PR が総ざらいより優先)
3. **依存関係の確認**: 修正対象の関数を呼んでいる側・呼ばれている側を洗い出し、修正で契約が変わる場合は呼び出し元も直す
4. **仕様書との突き合わせ**: docs/specs/ の該当仕様の全フィールドについて、検証が存在するかを表にする。穴があれば指摘されていなくても塞ぐ
5. **表引き否定テスト**: 全フィールド×全異常系(欠落/型違い/NaN/Infinity/負数/空/secret様/未知キー/順序違い/改ざんmanifest)のtable-drivenテストを書く。「Codexが次に探す場所」を先に全部埋めるのが目的
6. **重複統合**: コピペ重複していた検証ロジックは共通モジュールに統合する(実例: packages/memory/src/contract.ts)
7. **1commitで出す**: 総ざらいは意図が分かる1commitにまとめ、commit messageに調査範囲と確認方法を書く

**やってはいけないこと**: 指摘リストを上から順に1個ずつ直して即push(→次のレビューで隣のバグが見つかる無限ループになる。PR #2で実証済み)

## 重複PRの裁定手順(例: PR #1 vs PR #2)

1. 両方の diff / テスト数 / 設計文書との適合を比較表にする
2. 採用候補を1つ推奨し、根拠を3点以内で示す
3. 採用側の stale 解消(rebase)を Codex が行い、検証してから再提示
4. 不採用側の close は**ユーザーの操作**。closeコメント文案はCodexが用意する
