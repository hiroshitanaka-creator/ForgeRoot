# Adversarial Review Passes(G2: 敵対的セルフレビューの実行手順)

自分の差分に対して、**Codexレビュアーになったつもりで**以下の6パスを順に実行する。
各パスは `codex-finding-taxonomy.md` のクラスに対応する。パスごとに「探すもの」「具体的な手技」「合格条件」を定義する。

## 実行ルール

1. パスは P1→P6 の順に実行する
2. 1件でも発見したら記録し、orchestratorの点修正禁止ルール(4点セット総ざらい)で修正後、**P1からやり直す**
3. ゲート通過 = 全6パスを指摘ゼロで完走すること1回
4. 3周しても新規発見が止まらない場合は、設計欠陥(R1違反が典型)。実装のツギハギをやめ、G0からやり直す
5. 各パスの結果(発見数・修正内容)はgate reportに記録する

## P1: 改ざんパス(対C1, C6)— 最重要

**視点**: 「createの出力を保存し、1フィールドだけ書き換えて読み戻したら、validateは落ちるか?」

手技:
- validate系関数の本体を読み、**createが検証している項目のリスト**と**validateが検証している項目のリスト**を並べて差分を取る。validate側に無い項目が1つでもあれば発見
- 出力manifestの全フィールド(ネスト含む)を列挙し、各フィールドについて「この値を書き換えたらvalidateのどの行が落ちるか」を指差し確認する。答えられないフィールドが発見
- 導出フィールド(digest / 決定的ID / lineage_events / diff summary)は「再計算して比較しているか」を確認。存在・型チェックだけなら発見

合格条件: 全フィールドについて「書き換え → validateが落ちる行」を特定できる(= tamper-harnessが通る状態)。

## P2: fail-openパス(対C2)

**視点**: 「enum値に、仕様に無い文字列を入れたら通ってしまわないか?」

手技:
- `===` / `!==` で特定の文字列と比較している箇所を全てgrep(`grep -n '[!=]== *"' src/`)
- 各箇所について「これはallowlistか、denylistか」を判定。denylist(悪い値を弾く形)は発見
- status/decision/kind/mode等の分岐で、`else` に落ちた未知の値がrejectされずに処理継続する箇所は発見
- 未知キー: 入力オブジェクトのキーを列挙して既知キーと突き合わせているか確認

合格条件: 全enum系フィールドがallowlist検証されており、未知キーの方針(保存/拒否)が仕様に明記されている。

## P3: 不可能値パス(対C3)

**視点**: 「構文は正しいが意味的に不可能な値を流し込む」

手技:
- timestamp: `2026-99-99T99:99:99Z` / `2026-02-30T00:00:00Z` を頭の中で(またはREPLで)通す。正規表現のみなら発見
- 数値: `NaN` / `Infinity` / `-1` / `0` / 上限+1 / `1e309` を各数値フィールドに流す
- 文字列: `""` / `" "` / 上限+1文字 / secret様文字列(`ghp_...`, `-----BEGIN`)
- URI/パス: suffix空 / `..` 入り / 正準プレフィックス違い

合格条件: 全フィールドで構文検証の後に意味検証がある。

## P4: リプレイパス(対C4)

**視点**: 「複数opの組み合わせで、単独opでは起きない状態を作る」

手技(multi-op patchを受けるコードがある場合のみ):
- 「replaceで名前を空けてから同名add」(正当なのに拒否されないか)
- 「replaceで名前を変えた後に旧名add」(最終状態が重複するのに受理されないか)
- 「removeしてから同じものをremove」「addしてからreplace」等、op間に依存がある系列を最低4系列考える
- 検証コードが `existingTools`(元状態)と比較しているか、working state(リプレイ状態)と比較しているかを読む。元状態のみなら発見

合格条件: 検証がworking stateに対して行われ、最終状態の不変条件検証がある。

## P5: 網羅パス(対C5, C9)

**視点**: 「仕様の全フィールドが、検証・digest・summary・正規化のそれぞれで漏れなく扱われているか」

手技:
- design-rules R6の4列表(検証/digest/summary/否定テスト)を実際に作る。空セルが発見
- digest計算のコードを読み、hash対象に入っていないフィールドを列挙する
- diff summary生成コードを読み、変更を検出する対象フィールドの一覧と、仕様上変更があり得るフィールドの一覧を比較する
- allowlist(namespace等)が適用されるフィールドを列挙し、同種の値(route名等)が現れる他のフィールド(fallback等)に同じallowlistが掛かっているか確認
- 正規化経路(readTools等)を通るデータについて、「触っていないエントリのフィールドがround-tripで保存されるか」を確認。黙って消えるなら発見

合格条件: 4列表に空セルが無い。digestはcanonical全体をhashしている(または除外フィールドが仕様に明記されている)。

## P6: 境界・整合パス(対C7, C8, C10)

**視点**: 「クラッシュ・名前の食い違い・グラフの腐敗」

手技:
- validate系関数に `null` / `{}` / ネスト欠落オブジェクトを流して、throwせず `{ ok: false }` が返るか机上トレース。ガード無しのネスト参照(`x.review_gate.risk` 直参照等)をgrepで探す
- early returnの前後を確認: 入力エラーで先にreturnすると、高リスク分類(forbidden target等)が隠れないか
- blueprint interface registryの正準API名をgrepし、exportと突き合わせる
- グラフ系: 祖先方向・子孫方向・自己参照の3方向のcycleチェックが存在するか確認

合格条件: throwしない契約が守られ、正準名がexportされ、グラフ3方向チェックがある(該当コードがある場合)。
